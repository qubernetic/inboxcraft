# 445

## Changelog
### Added
- An agent can ask the owner to allow one `owner` command: `inboxcraft-cli --ask-owner <command>` (or a control
  channel line with `"ask_owner": true` and the client's name) sends the request to the running InboxCraft, where it
  waits in the window's queue, at most eight at a time, until the owner allows or denies it; it runs for the owner
  only on Allow, as one step of the window's undo that the agent cannot take back. No answer within two minutes is a
  refusal. The answer is the command's own, or `denied`, `timed_out` or `busy`; on a store (`--store`) or with no app
  running it is refused. Such a line may be up to 8 MiB, and `--params-file <path>` reads the parameters from a file
  (#445)

## Gaps
- An owner request's client name is what the client says of itself; nothing checks it, and the window shows it as
  the name the program calls itself (#445).
- The control channel's eight client places and the owner-request queue's eight places are the same number: eight
  waiting requests hold every client place, so meanwhile other clients (safe ones and the MCP bridge too) are
  answered `busy`, and over the socket a ninth asker gets the connection cap's `busy` before the queue's own (#445).
- A control-channel line that says `"ask_owner": true` may be 8 MiB whatever its command, also a `safe` one, which
  runs at once as the agent's (#445).
- An asker that only closes its writing side of the socket is taken for gone, and its request is withdrawn. Once the
  owner has pressed Allow the command runs even if the asker leaves meanwhile; when InboxCraft ends between the press
  and the answer, the asker is told `closing` and the command may have run (#445).
- The sentence of the same code differs between the window and the server (`timed_out`), so a client matches on the
  code only (#445).
